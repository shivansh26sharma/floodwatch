# FloodWatch

District-level flood **onset** prediction for India, built entirely from freely
available data — 3rd-year machine learning project, Thapar Institute.

The model answers one question for every district, every day: **will a flood
begin here within the next seven days?** It is deployed as a public warning
page with a technical console behind it:

**[floodwatch26.streamlit.app](https://floodwatch26.streamlit.app)**

Anchored to a documented historical event (**Kerala 2018**) so the system can
be validated against what actually happened, rather than making untested
predictions.

### Headline results

Measured on a held-out chronological test split — 56,210 district-days from
2017–2023 containing 130 recorded flood onsets, with the alert threshold fixed
on validation and applied unchanged.

| | Logistic | Random forest | XGBoost |
|---|---|---|---|
| Events warned (of 130) | **86 — 66.2%** | 68 — 52.3% | 88 — 67.7% |
| Median lead time | **13.0 days** | 5.0 days | 9.0 days |
| Alarm duty cycle | 15.8% | **11.6%** | 17.0% |
| PR-AUC | **0.082** | 0.046 | 0.043 |
| Brier score | **0.0154** | 0.0159 | 0.0161 |
| Expected cost at 20:1 | **16,490** | 16,637 | 16,772 |

Logistic regression is the operational choice and the dashboard default: the
lowest expected cost, the longest notice, the best Brier score. XGBoost finds
two more events and pays 682 extra false alarms and four days of notice for
them. The simplest model winning is a finding, not a failure — see
*Two design decisions worth defending in the viva* below.

Secondary task: **no forecasting method tested beats persistence** at
predicting river discharge, at any horizon.

## Getting real data

Two commands. The first needs ordinary internet access, so run it on your
own machine.

```bash
python -m src.data.download        # ~20 min for 75 districts, 2000-2023
```

That pulls, for every district in `src/data/districts.py`:

| What | Source | Registration |
|---|---|---|
| Daily rainfall | ERA5 reanalysis via Open-Meteo archive API | none |
| Daily river discharge | GloFAS via Open-Meteo flood API | none |
| Elevation, slope, ruggedness | Copernicus DEM via Open-Meteo | none |

It also writes `data/raw/provenance.json` — source, URL, parameters,
retrieval time, row counts. **That file is your dataset lineage section.
Do not delete it.**

### Then the labels, which are a manual download

From the DFO Zenodo record <https://doi.org/10.5281/zenodo.19288170>
download **`Global_Flood_Records.gpkg`** and save it as
`data/raw/Global_Flood_Records.gpkg`.

**Take the GeoPackage, not the CSV.** DFO's redesigned v0.9.0 release
dropped the free-text location column its older archive carried — the CSV
now identifies an event only by *country*, which cannot place a district.
The GeoPackage carries the actual flood polygon per event, so districts are
labelled by a spatial join: a district is flooded on a day if its point
falls inside that event's footprint. That is strictly better than text
matching — no name collisions, and no state-level fallback smearing one
district's flood across a whole state.

The data is CC0 / CC-BY-4.0, so you may redistribute it. Cite it anyway.

Then:

```bash
# config.yaml
data:
  source: real        # was: fixture
```

```bash
./scripts/run_pipeline.sh
```

### Say this accurately in your report

ERA5 and GloFAS are **reanalysis**, not station gauges: physics-based models
that assimilate large volumes of real observations to produce a gridded,
gap-free record. They are real data — not synthetic, not generated by us —
and they are standard inputs in published flood research. But ERA5's ~25 km
grid smooths local extremes and will under-represent peak intensity during an
event like Kerala 2018, and GloFAS discharge is modelled routing rather than a
CWC gauge reading. Claiming station observations when you used reanalysis is
exactly the kind of thing an examiner catches. The honest version is
perfectly defensible.

Cite: Copernicus Climate Change Service (ERA5), Copernicus EMS (GloFAS),
Copernicus DEM, and Open-Meteo.com, which serves all three free for
non-commercial use.

### Two things that will bite you

**Sparse labels.** DFO records only *large* events, so the positive class is
well under 1% — far rarer than the fixture suggests. Rank models by PR-AUC,
not ROC-AUC, which flatters badly at this imbalance. If a split ends up with
zero flood days the trainer stops with an explanation; widen
`project.start_date` rather than shuffling the split.

**Label attribution.** Labels come from a spatial join against DFO event
polygons, which is precise, but three caveats remain and the loader prints
the numbers for each run:

- DFO footprints are satellite-derived and generally coarser than a
  district, sometimes a bounding region rather than observed inundation. A
  district inside the footprint counts as flooded even if only part of it
  was.
- We test the district headquarters *point*, not its area, so a district
  whose HQ sits just outside a footprint reads as dry.
- Districts that no event ever intersected contribute only negatives. The
  loader names them — say how many there were.

### Narrowing the study region

`project.districts` in `config.yaml` accepts `all`, `basin:Brahmaputra`,
`state:Kerala`, or an explicit list. Training on one basin and testing on
another is the transferability experiment — whether flood models generalise
across basins is a genuinely open question, and a transferability matrix is a
stronger result than a single accuracy number.

## Switching to real data

One line in `config.yaml`:

```yaml
data:
  source: real      # was: fixture
```

Then implement the four loader functions in `src/data/loaders.py`. They are
the **only** place that needs to know each source's file quirks — everything
downstream is already written and tested against the canonical schema.

| Table | Source | What to implement |
|---|---|---|
| `rainfall` | IMD daily rainfall via [data.gov.in](https://data.gov.in) | Reshape wide/monthly files to long `date, district, rainfall_mm` |
| `river` | India-WRIS (CWC) gauge readings | Map stations to districts by lat/lon, aggregate to district-day **max** |
| `terrain` | SRTM DEM | One-off zonal stats job (rasterio + district boundaries); write CSV once |
| `labels` | [Dartmouth Flood Observatory](https://floodobservatory.colorado.edu/) archive | Expand each event (begin/end date + area) into district-days |

**The labels are the hard part.** DFO gives one row per event with a coarse
spatial extent; you must decide which districts each event covers and document
that decision. It is the single biggest source of label noise in the project
and your report should say so explicitly.

## Live / forward prediction

```bash
python -m src.live.fetch              # 92d history + 16d forecast per district
python -m src.live.predict --days-ahead 6
```

`fetch` pulls the same two variables from the same provider, from the
*forecast* endpoints instead of the archive ones. `predict` rebuilds the
training features over that window and scores today plus each forecast day,
so a district can show rising risk before anything has happened.

Two things make this honest rather than a demo:

**The feature reference is fitted once and reused.** Climatology departures
and percentile ranks are defined *relative to a reference distribution*. If
serving re-derived that reference from whatever 92-day window it happened to
have, identical rainfall would produce a different feature value than it did
in training — train/serve skew, the classic way a model that looked fine
offline quietly produces nonsense in production. So the reference is fitted
on the training split, saved to `outputs/models/feature_reference.pkl`, and
loaded back for every live prediction. If that file is missing, live scoring
**refuses to run** rather than improvising one.

**Forecast decay is reported, not hidden.** Every output row carries
`forecast_share`: how much of its 30-day feature window is numerical
forecast rather than observation. It climbs with lead time, and the console
shows it next to the risk, because a +6d number built from six days of
forecast rainfall deserves less weight than today's.

What is *not* fixed: the model was trained on ERA5/GloFAS reanalysis and is
served analysis + NWP forecast. Related products, not the same series. The
rigorous fix needs an archive of past forecasts, which we do not have — so
say so in the report instead of presenting live output as backtested.

### Forecasting (`src/models/forecast.py`)

```bash
python -m src.models.forecast                       # river level
python -m src.models.forecast --target rainfall_mm  # rainfall
python -m src.models.forecast --no-lstm             # skip the network
```

**The question is not "did the LSTM work" — it is "can anything beat
persistence?"** River levels are strongly autocorrelated, so "tomorrow equals
today" is a hard baseline to beat, and plenty of published hydrological deep
learning quietly fails to beat it. Every model is therefore scored with a
**skill score**:

```
skill = 1 - MAE_model / MAE_persistence       >0 better · <0 worse than doing nothing
```

Report negative skill if you get it. A measured, explained failure is a
finding; a hidden one is a problem waiting for the viva.

**MAPE is suppressed on rainfall.** It is undefined wherever the true value is
zero, and rainfall is zero most days. The module reports sMAPE instead and
says so. (Watch out: on zero-inflated series sMAPE saturates near 200% for
every model, so it barely discriminates — use MAE to rank.)

**ARIMA walks forward without refitting.** It is fitted once per district on
train, then advanced through the test period with `extend`, so each forecast
origin only ever sees past data. Refitting the parameters at every origin is
more rigorous and far too slow — that compromise is stated in the report
rather than left implicit.

> The first version used `append(refit=False)`, which re-filters the entire
> series on *every* call — O(n²) Kalman passes. It ran for over an hour on 22
> districts without finishing. `extend` continues from the existing filtered
> state, which is what a walk-forward loop actually needs: same forecasts,
> about a second per district.

**Models are compared on identical rows.** ARIMA is evaluated at strided
origins and only in districts where the fit converged, so scoring it on its
own output compares it against baselines on a different, easier row set — it
appeared to beat persistence at 7 days by 1% of MAE. `matched_comparison`
restricts every method to the forecast origins all of them produced; the
advantage vanishes (+0.010 → −0.001). `forecast_matched_*.csv` is the table
to cite; `forecast_comparison_*.csv` is the unmatched one.

## Two design decisions worth defending in the viva

**1. We predict forward, not sideways.**
The target is a flood at `t + horizon` using only features available at `t`
(default horizon: 1 day). Predicting today's flood from today's rainfall gives
a beautiful ROC curve and **zero warning time**, which is useless. Change the
horizon with `--horizon 3`.

**2. Accuracy is not the headline metric. Lead time is.**
A model that is 95% accurate with 40 minutes of warning saves nobody; one that
is 80% accurate with 18 hours saves a district. `evaluate.py` reports median
lead time per event — alongside the **alarm duty cycle**, because lead time
alone is gameable: a model that keeps the alarm on all monsoon shows enormous
lead time and is operationally worthless. Good systems have long lead time
*and* a low duty cycle.

Also deliberate:

- **The threshold is not 0.5.** It is chosen on the validation split to
  minimise expected cost at a 20:1 miss-to-false-alarm ratio (`config.yaml`),
  then applied unchanged to test. Picking it on test would be cheating.
- **The output is a calibrated probability.** Class reweighting is what lets
  the model see a 1.6% positive class at all, and it is also what destroys the
  probability scale: raw mean predicted risk was 0.269 against an actual onset
  rate of 0.016, and every model lost to always-predicting-zero on Brier.
  `src/models/calibrate.py` fits a monotone isotonic map on 90,332
  out-of-sample predictions from the **training period only** — the validation
  split is already spent choosing the threshold — and pickles it with the
  model, so the dashboard and the live scorer apply exactly what was fitted at
  training time. Logistic Brier falls 0.162 → 0.015.
- **The threshold then lands where theory says it should.** At a 20:1 cost
  ratio the optimal alarm point is 1/21 = 0.048. Sweeping validation returns
  0.03, 0.06 and 0.09 for the three models. Before calibration the same sweep
  returned 0.71 and 0.41, because the threshold was absorbing the inflation
  rather than expressing a decision rule.
- **Logistic Regression is a real baseline.** If RF and XGBoost don't beat it,
  report that. It's a finding, not a failure.
- **Climatology is fitted on the training period only** — a subtle and very
  common leak.

## The case where the model beat the archive

Worth knowing before anyone asks why precision is 6%.

Kerala, August 2018. The flood peaked on 15–17 August; Thrissur was badly
hit. Score that week and the logistic model gives Thrissur **0.031 on the
14th, 0.085 on the 15th, 0.047 on the 16th** — calibrated probabilities,
against an alert threshold of 0.03 and a base rate of 0.016. It raised the
alarm two days early, held it through the peak, and at its height put the
district at more than five times normal risk. Discharge went from 22 to
85 m3/s in two days.

The label for every one of those days is **0**, so every one of those alarms
was counted as a false positive.

Two separate failures stack up:

1. **The event is not in the archive.** DFO's only Kerala-area event
   overlapping August 2018 runs 7–10 August with 20 fatalities — the first
   wave. The catastrophe of 15–17 August, with a death toll reported in the
   hundreds, has no record. The nearest candidate, an India event dated
   15 Aug – 7 Sep, has its polygon at 93.7–95.8E / 24.9–27.2N — Nagaland and
   Manipur, about 23 degrees away.
2. **Thrissur's point misses the polygon that does exist.** For the 7–10
   August event, the district's sample point falls 0.029 degrees — roughly
   3 km — outside the footprint. Palakkad and Wayanad miss it too.

Across the Kerala basin, 11–20 August 2018, the model raised 21 district-day
alarms in 7 districts, all scored false — a fraction of a per cent of the
logistic model's 8,370 reported false positives, from one episode.

**What this means for the numbers.** The reported precision of 0.057 is
*pessimistic by an unknown amount*, because an unknown share of the false
alarms are real floods the archive does not record. That is a much stronger
thing to say than "precision is low because of the cost ratio", and it is
checkable: `src/data/loaders.py` does the labelling, and the GeoPackage is a
CC0 download anyone can inspect.

Reproduce it:

```bash
python - <<'PY'
import pickle, pandas as pd
d = pd.read_parquet("data/processed/features_h1.parquet")
b = pickle.load(open("outputs/models/risk_logistic_h1.pkl", "rb"))
d["risk"] = b["model"].predict_proba(d[b["features"]])[:, 1]
w = d[(d.district == "Thrissur") & (d.date >= "2018-08-13") & (d.date <= "2018-08-17")]
print(w[["date", "rainfall_mm", "river_discharge_m3s", "risk", "flood_occurred"]])
PY
```

The random forest, for the record, peaked at **0.017** that week against its
own 0.46 threshold. It missed the largest flood in the record completely,
which is why the dashboard defaults to logistic regression.

## What shipped, and what was dropped

The original proposal was a multimodal system: riverine risk classification,
satellite inundation segmentation, speech-to-text on citizen voice reports, a
fusion layer and a GIS dashboard. Scoping it down to one thing done properly
was the right call, and the report says so rather than implying the rest was
always out of scope.

**Shipped.** The riverine core end to end: dataset build, 59 leakage-controlled
features, three calibrated classifiers, cost-sensitive thresholding, lead-time
evaluation, five forecasting baselines, SHAP explanations, live forward
prediction from a public feed, a public warning page and a technical console,
a deployed URL, 25 tests, and a 25-page report.

**Dropped, deliberately.** Satellite CV (Sen1Floods11 segmentation) and the
speech/NLP citizen-report track — both were a project each, and neither would
have been honest in the time available. The console reserves a place for the
citizen-report feed.

**Not run.** The LSTM forecasting baseline. On the evidence of the five methods
that did run, it would have to beat persistence to be worth deploying, and
nothing else did.

## Honest-reporting rules

1. No number from the fixture appears in the report.
2. Report recall before accuracy — recall is the metric that corresponds to
   people not being warned.
3. Report the bad numbers too. Measured, explained limitations score better
   than hidden ones, and far better than ones found for you in the viva.
4. Document dataset lineage: source, download date, URL, licence, coverage,
   record counts, and every preprocessing step.
5. The system recommends; a human decides. Never frame it as automated
   evacuation.
